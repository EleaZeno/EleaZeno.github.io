## 先说结论

- 推理加速里有一类反直觉的问题：**为了省钱加的那个"廉价"组件，自己变成了瓶颈**。这周的三篇论文都在处理同一个模式。
- 投机解码（speculative decoding）的经典假设是"草稿模型便宜到可以忽略"。在百万 token 上下文里这个假设直接失效：草稿头每走一步都要读一遍全量 KV cache，读取量随上下文线性增长。
- 修法出人意料地朴素：**只给草稿加滑动窗口，验证仍走全注意力**。因为最终接受哪个 token 由全注意力的目标模型决定，所以窗口化不改变输出分布——它只改变"提议什么"，不改变"接受什么"。
- Agent 场景有一个平行版本：工具沙箱要么常驻烧内存，要么按需启动吃冷启动。SpecBox 的做法是在**模型还在吐 token 的时候就猜出接下来要调哪个工具**，把沙箱启动和推理重叠掉。
- 这三件事的共同结构是：把"什么时候做"从关键路径上挪走，而不是把"做什么"变快。

## 投机解码为什么会算亏

先把机制讲清楚。自回归生成一次只出一个 token，GPU 大量时间在等显存搬数据而不是算。投机解码的思路是：让一个便宜的草稿模型先猜 k 个 token，再让贵的目标模型**一次并行验证**这 k 个。猜对了就一次前进多步，猜错了退回去。

关键在于它是**无损**的：目标模型对每个 token 都做了它本来要做的检查，所以最终输出分布和不用投机时一致。这不是近似加速，是纯粹的调度优化。

现在的前沿模型往往自带一个 MTP（Multi-Token-Prediction）草稿头，共享主干权重，看起来几乎免费。问题出在这里。据 Windowed-MTP 这篇的描述，MTP 草稿头在每个草稿步都要对**整个 KV cache** 做全注意力。设上下文长度为 `T`，草稿深度为 `d`：

```text
草稿读取量 ∝ d × T        （每步都读全量）
验证读取量 ∝ T            （并行一次）
```

`T` 小的时候 `d × T` 无所谓。`T` 到一百万时，草稿的读取量反而盖过了验证。作者明确指出一个后果：**草稿越深可能越慢，深到一定程度净收益变负，比完全不用投机还慢**。而且这个问题在混合/线性注意力的模型上更尖锐——验证本身变便宜了，草稿的全注意力读取就更显眼。

这是个很好的工程教训：一个组件的"便宜"是相对于它旁边那个组件的。把旁边那个优化掉之后，便宜的东西就变成贵的了。

## 修法：只窗口化草稿

Windowed-MTP 的做法是把 StreamingLLM 那套**滑动窗口 + attention sink** 只用在草稿的注意力上，验证保持全注意力不动。

为什么这样是安全的，值得说清楚，因为这是全篇最漂亮的一点：

- 草稿的职责只是**提议**候选 token
- 目标模型的职责是**决定**接受哪些
- 窗口化只让草稿看得少了，于是它可能提议得差一点（接受率可能降）
- 但被接受的 token 仍然是全注意力目标模型验证过的

所以按构造就是无损的：输出分布不变，最坏情况只是接受率下降导致加速比变小。作者称这把草稿的 KV 工作集**限制为常数**，在 1M 上下文下丢掉约 99% 的 KV 条目。

报告的效果：在三个架构族（Qwen GDN-MoE 35B/122B，以及一个 Mamba2-hybrid NoPE 120B）、1M 上下文、单卡 SGLang 上，每个解码步的开销比出厂的原生 MTP 草稿降低 **28% 到 44%**。另外那部分再也不会被读到的草稿 KV（1M 时占总 KV 的 7.7–11%）用一个环形缓冲回收掉。

需要标注边界：这是单篇预印本、单人作者、v1，没有经过同行评审。机制推理是自洽的，数字我没有独立复现。

## 同一个套路，换到 agent 上

SpecBox 处理的是另一个场景，但结构一模一样。

LLM agent 现在普遍通过 MCP 调用隔离的外部沙箱。部署上有个两难：

- **常驻沙箱**：随规模增长内存开销过大
- **按需启动**：冷启动惩罚严重，多租户多轮场景下尾延迟很难看

SpecBox 的核心动作是**投机式沙箱预分配**：用关键词匹配加流式语义 embedding，在**模型还在生成 token 的中途**就识别出接下来大概要调什么工具，把沙箱的启动过程和推理完全重叠掉。再往前一步，它用一张沙箱依赖图做上下文感知的随机预取，跨多个 agent 步骤提前猜。

配套还有两个正交优化：语义结果缓存（砍掉重复调用），以及一条走共享内存的带外传输通道（绕开网络序列化，做零拷贝产物传递）。

报告数字：在高并发多轮 agent trace 上，P99 端到端延迟相比按需启动基线降低最多 **2.9 倍**，峰值内存相比永久常驻降低 **45.9%**。

注意这两个数字是分别对照两个不同基线的——它同时改善了那个两难的两端，这才是重点。

## 第三篇：把选择的成本也降下来

LOCKS 处理长上下文解码的另一面。KV cache 的问题是每个解码步都要**完整读一遍**。已有的做法是只读"重要"的部分，但选择本身也要读 key 才能判断重要性。

它的观察是：注意力的 key **局部低秩、全局高秩**。也就是说，共享一组低秩基会丢掉每一页自己的特殊方向，但每页用自己的紧凑基就能保留。于是给每页一份自己的谱摘要（常驻，约为 cache 的十分之一），在页内重建 logits，用 log-sum-exp 估计每页的注意力质量，只对 top 页做注意力——**选择过程本身不读任何候选 key 或 value**。

报告效果：在 2048 token 预算下，100K+ 上下文时聚合质量与 FullKV 相当，而只对约 2% 的 token 做注意力；1M 时每 token 解码延迟减半（2.0×）。作为不改动 vLLM 的插件发布。

## 边界

- 三篇都是 v1 预印本，都未经同行评审，数字均为作者自报，我没有复现。
- 三者的收益都强依赖于**长上下文**。在几千 token 的常规对话里，这些优化的收益会小得多甚至为负。
- Windowed-MTP 的无损性是就"输出分布"而言的，不是"加速比稳定"——接受率下降多少依赖具体模型和输入。
- SpecBox 的预测式预热在猜错时会浪费资源。论文报告的是聚合指标，猜错率在什么条件下会失控，摘要里没有交代。
