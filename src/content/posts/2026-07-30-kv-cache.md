## 先说结论

- 对自回归生成来说，**KV Cache 的价值是把每步重复计算，改成一次计算后反复读显存**。不做缓存时，每生成 1 个 token 都要把历史 token 的 K、V 重新算一遍；做了缓存后，只需要算当前 token 的 Q、K、V，再拿 Q 去和历史 K、V 做注意力。
- 代价也很直接：**算力压力下降，显存容量和显存带宽压力上升**。很多线上推理瓶颈最终落在 HBM 带宽，而不是 FLOPS。
- KV Cache 优化的主线只有三件事：**少存、快读、减少碎片**。分别对应 GQA/MQA、连续/分页缓存管理、批处理调度。

## KV Cache 到底缓存了什么

Transformer 解码时，第 `l` 层对当前 token 会产生一组 `K_l` 和 `V_l`。历史 token 的这些 K/V 在后续步骤不会变，所以可以缓存起来。

如果当前序列长度是 `T`，隐藏维度是 `d_model`，注意力头数是 `h`，单头维度通常是 `d_head = d_model / h`。对标准 MHA，单层缓存大小近似是：

```text
bytes_per_layer = 2 * T * h * d_head * dtype_bytes
```

前面的 `2` 是 K 和 V 两份。整个模型再乘层数 `L`：

```text
total_kv_bytes = 2 * L * T * h * d_head * dtype_bytes
```

因为 `h * d_head = d_model`，也常写成：

```text
total_kv_bytes = 2 * L * T * d_model * dtype_bytes
```

举个常见量级：若 `L=32`、`d_model=4096`、`T=4096`、KV 用 FP16/BF16 即 2 字节，那么单条序列的 KV Cache 大小约为：

```text
2 * 32 * 4096 * 4096 * 2 = 2,147,483,648 bytes ≈ 2 GiB
```

这个数字的适用条件很明确：**标准 MHA、32 层、4096 hidden、上下文 4096、每个 KV 元素 2 字节**。如果模型用 GQA/MQA，KV 头数会减少，实际缓存会更小。

## 为什么它能提速，但不一定让 GPU 更“忙”

prefill 和 decode 要分开看。

- **Prefill**：把整段 prompt 一次性送入模型，attention 更像大矩阵乘，通常更吃算力。
- **Decode**：每步只生成 1 个或少量 token，虽然避免了重复算 K/V，但要频繁读取历史 KV，所以更容易受显存带宽限制。

这就是为什么很多服务在长上下文、小 batch、低并发下，GPU 利用率看起来不高，但延迟还是不低：不是没活干，而是**在等显存搬数据**。

## 真正有用的优化点

## 1. 用 GQA/MQA 减少 KV 体积

标准 MHA 里，每个 query head 都有自己的 K/V head。GQA（Grouped Query Attention）让多个 query head 共享一组 K/V；MQA 则更极端，所有 query head 共享 1 组 K/V。

效果：KV Cache 大小近似按 `kv_heads / q_heads` 缩小。

例如 `q_heads=32`，若是 `kv_heads=8` 的 GQA，则缓存约是 MHA 的 `8/32 = 1/4`。对长上下文和高并发很有价值。

代价：表达能力可能下降，具体影响依赖模型训练时是否就是按 GQA/MQA 设计。**不能把一个已训练好的 MHA 模型随便改成 MQA 直接上线**。

## 2. 分页式 KV Cache，解决碎片和搬移

线上服务不是单条请求顺序跑，而是很多请求动态进入、结束、续写。若给每条序列预留一大块连续显存，会有两个问题：

- 短请求提前结束，留下碎片
- 序列增长时可能需要搬移整块缓存

常见做法是**paged KV cache**：把 KV 按固定大小的 block/page 存，逻辑上连续，物理上可离散，再用索引表映射。这样做的好处：

- 分配回收更像内存页，碎片少
- 序列扩展时只追加页，不搬历史数据
- 更适合 continuous batching

代价是多一层地址索引，kernel 实现更复杂；页太小会增加索引和调度开销，页太大又浪费尾部空间。

## 3. 连续批处理比静态 batch 更重要

decode 阶段每个请求生成速度不同，静态 batch 很快就会“空洞化”。连续批处理会在每一步把新请求插进来，把结束的请求移出去，尽量维持有效 batch。

它和 KV Cache 是绑定关系：没有可灵活分配的 KV 管理，continuous batching 很难做得好。

## 4. 量化 KV Cache

除了权重量化，也可以对 KV 做更低比特存储，比如 INT8，甚至更低。直接收益是显存占用减半或更多，间接收益是减少带宽压力。

但这里取舍比权重量化更敏感：KV 是运行时状态，误差会随着长序列不断参与注意力，可能更容易影响长文本质量。是否可用，要看具体模型、上下文长度和量化校准方法，不能只看短 prompt 的 benchmark。

## 一个容易混淆的点

KV Cache **不会改变注意力对历史长度的访问需求**。它省掉的是“重新计算历史 K/V”，不是把注意力复杂度从根上消掉。decode 时当前 token 仍然要看全部历史 token 的 K/V，所以长上下文下，读取成本还在。

这也是为什么很多所谓“长上下文优化”，本质上不是 KV Cache 本身，而是配合滑动窗口注意力、块稀疏注意力或状态压缩。那些方法改的是“看多少历史”；KV Cache 改的是“历史状态怎么存和复用”。
